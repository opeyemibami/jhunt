# 0017: UI v1, the whole flow in the browser

Status: accepted, approved by the owner on 2026-11-02 before any code. UI v1 comes before search profiles (owner, priority change).

## Context

Every step works from the command line: Scout, Capture, pack drafts, submissions and facts. The owner wants to run the whole flow in the browser. The digest page (ADR 0012) is the start: server-rendered FastAPI on 127.0.0.1, with Host and Origin checks and no login.

## Decision

**Shape**:
- Server-rendered pages from the existing FastAPI app, with plain HTML forms.
- **No new frontend dependency.** The only JavaScript is small inline scripts for live updates and copying.
- `python-multipart` is approved. It arrived with U4, because FastAPI needs it for any form field, not only uploads.
- **Still 127.0.0.1 only**, with the same checks: `Host` on every request, `Origin` on every form post. Every value from a board or a model is escaped, and there's no login until the Cloud Run migration.

**PRs, in order**:

| PR | What |
|---|---|
| U1 | `jhunt-up`, `jhunt-down`, `jhunt-logs`; this ADR |
| U2 | Digest: "Run Scout now" (the once-a-day rule; Retry after a failure; Rescore after a success) |
| U3 | `/applications` and `/applications/<id>`: the stored job description, stage, events, submissions, drafts |
| U4 | The pack on the application page: draft; accepted and blocked claims side by side with reasons; edit a line; copy the cover note |
| U5 | Record a submission from the application page: upload, channel, confirm; the same storage and guarantee as `jhunt-submission` |
| U6 | The Facts page: edit text, evidence, level and aliases; retire; each save a new version |

U7, the Targets and Sources pages with a re-ranking preview, **moves into the search-profiles work**. The owner gets the profiles plan after U6, and U7 is built as part of it, on versioned tables.

**The owner's answers**:

1. **Live updates.** Anything that queues a run (Capture, Run Scout, Draft pack, Record submission) **updates in place, without a page reload**: queued, then running, then the result or the failure reason.
   - A small inline script polls a run-status endpoint with `fetch` and updates only the status element.
   - A `<meta http-equiv="refresh">` is the fallback, used only if the script doesn't load.
   - No new frontend dependency.
2. **Showing the job description.** The web app reads records **directly with `RecordStore.get`**, for display only, by exact generation with the sha256 checked. **This is a read-only exception to "every storage call through the tool gateway"** (hard rule 2, ADR 0008): it changes nothing, and nothing is decided on it. Writes, and reads that feed a workflow, still go through the gateway.
3. **Copy cover note.** A clipboard button (a small inline script), with a read-only text area as the fallback.
4. **Facts: the database is the source of truth.**
   - `jhunt-facts export` writes the owner's file from the database. The file must still be outside any git repository.
   - `jhunt-facts import` refuses if any fact was edited in the browser since the last export, unless given `--overwrite`.
5. **Targets and Sources** move to versioned tables, inside the profiles work. For the re-ranking preview, `postings` gets a `description_text` column, filled by Scout, so scores can be recomputed without reading staging.
6. **Starting and stopping** is a supervisor command, not containers. Containers come with the Cloud Run migration, which needs a Dockerfile anyway.

**`jhunt-up`, `jhunt-down`, `jhunt-logs`** (U1):
- **`jhunt-up`**:
  1. starts the database (`docker compose up -d --wait db`) and runs `alembic upgrade head`;
  2. starts `jhunt-worker` and `jhunt-api` as background processes, each in its own session, so a Ctrl-C in the terminal doesn't reach them. It waits until the worker logs that it started and the web app answers on `127.0.0.1:<JHUNT_API_PORT>`;
  3. records their PIDs under `.jhunt/` (git-ignored), with **each service's log in `.jhunt/logs/<service>.log`**;
  4. refuses if they're already running. If a service doesn't come up, it stops what it started and shows the end of that service's log;
  5. warns about any other `jhunt-worker` already running, which would also claim runs.
- **`jhunt-down`**:
  - sends SIGTERM to the worker and web app and waits for them. The worker finishes the run it's on first; it's killed only with `--force`;
  - checks that each PID is still a jhunt process before signalling it, so a reused PID is never touched;
  - leaves the database running unless given `--db`.
- **`jhunt-logs`** follows every service's log, each line prefixed with its service (`--lines N` to start further back; `--no-follow` to print and exit).
- Settings come from the environment, as everywhere else (`uv run --env-file .env jhunt-up`). The processes it starts inherit it, and nothing reads `.env` itself.

**U2 notes**:
- **Shared rules**: Scout's once-a-day, Retry and Rescore rules moved from `jhunt-scout` into `jhunt.workflows.scout.start` (`start_scout`, `latest_today`), so the command and the digest follow the same rules. `jhunt.api` may not import `jhunt.app`. Each keeps its own wording for a refusal.
- **Live status**: `jhunt.api.live` holds the run-status text, the status element, the polling script and the `<noscript>` refresh, for U3 to U5 to reuse. `GET /runs/<id>` gives `{status, text}`: the summary for a Scout run that succeeded, `failed: <error>` for any that failed.
- **Test isolation** (owner, after U1): tests that run docker compose use their own project, `jhunt-test-<id>`. `tests/compose_guard.py` refuses, before it starts, any test process that runs compose, `jhunt-up` or `jhunt-down` without one.

## Consequences

- One command starts everything on the owner's machine. Logs are in one folder, and processes survive the terminal that started them.
- The supervisor is local only: on Cloud Run, the platform starts the services.

**U4 notes**:
- **Draft pack** on the application page queues a new draft on thread `pack-<id>-<n>`, with n one more than the application's drafts so far, and shows its status live: "draft N: X accepted, Y blocked".
- **`/drafts/<id>`** shows the round the draft uses: accepted claims on the left (the framed cover note, the CV lines with their facts) and blocked claims on the right with their reasons. When there was a repair, the first draft's blocked claims are shown too. Blocked claims are shown as drafted and can't be edited (hard rule 6).
- **An edit** of an accepted line is a new row in `draft_edits` (version 1, 2 and so on; `created_by` is "you"; append-only), plus a `draft_edited` label holding the text before and after. The claim validator runs on the new text against the line's cited facts. Its problems are shown as warnings on the line and never block the save: the owner wrote it, and the owner sends it.
- **The cover note to copy** is built from the latest version of each sentence.
- `jhunt-applications delete` also removes an application's draft edits and draft labels.
